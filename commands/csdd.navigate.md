# /speckit.csdd.navigate

新增模块、新建文件或实现新功能之前使用：先看清现有结构，复用优先，改动最小。**一路做完，不要中途停下来让用户去执行命令。**

用户要做的事：

$ARGUMENTS

## 步骤

1. 运行（没有架构地图时自动生成骨架）：

   ```
   bash .specify/extensions/csdd/scripts/csdd-navigate.sh --target . --init-map
   ```

   把退出码和输出原样放进回复。脚本找不到 bash 5.2 以上、或没装 blueprint-index / brownkit 时，输出里会说明，照实转述，不要自行安装扩展。

2. 确定要做的事：优先用上面 `$ARGUMENTS`；为空就从本次对话里提炼。**只有两者都没有时**，才问用户一句“要新增或修改什么”，其余步骤不要再提问。

3. 按这件事的范围，**自己读代码**找职责相近的现有实现：用 Grep、Glob、Read，不要只凭文件名或目录名判断。涉及的模块在步骤 1 的清单里挑。

4. 给出复用结论，四选一：直接复用 / 配置 / 适配 / 无满足条件，并写明依据（文件路径和你读到的内容）。

5. 若是修改已有功能，先找出实际被入口调用的那个实现，记录依据和证据等级（静态确认 / 运行时确认 / 推断 / 未知）。证据不足写“未知”，不要猜。

6. 步骤 1 若报告 UNMAPPED 或 STALE，把清单列在结论后面，说明哪些与本次工作有关；不要自行 remap 或改地图。

## 要知道的限制

- 骨架地图只有按目录切分的结构，没有说明文字；它能让 `check` 在以后发现新增目录和代码变动，不代替阅读代码。
- `blueprint-index` 的 `check` 是确定性漂移门禁，不做代码检索；需要 bash 5.2 以上。
- 步骤 3、4 的判断由你完成，脚本只提供输入，不保证判断正确。

## 不要做

- 不要因为脚本输出“in sync”就认为不存在重复实现。
- 不要为了通过检查而改地图或删文件。
- 不要把“请你运行 xxx 命令”当作结论交还给用户，除非那条命令需要用户的凭据或授权。
