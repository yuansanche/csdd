# 架构基线与设计约束

本文件是复杂系统的通用架构基线，未指定业务应用、JDK、数据库或部署规模。接入真实项目后在 ADR 中固定技术栈，并把下面的逻辑边界映射为实际模块。小团队优先清晰的模块化单体；只有独立部署等实际需求成立时拆服务。

## 模块契约

| 逻辑模块 | 职责 | 允许依赖 | 禁止事项 |
|---|---|---|---|
| 接入适配器 | HTTP / 消息 / UI 输入验证与协议转换 | 应用接口 | 直接承担领域决策、跨模块改数据库 |
| 应用层 | 用例编排、授权上下文、事务协调 | 领域模型、端口接口 | 暴露内部持久化对象、形成循环依赖 |
| 领域层 | 业务规则、不变量与状态转换 | 本领域的值对象和抽象契约 | 直接依赖 Web 框架、数据库实现或外部网络 |
| 基础设施适配器 | 数据库、模型、第三方服务实现 | 应用 / 领域定义的端口 | 让业务层依赖具体客户端实现 |

这是逻辑职责约束，不强制每个小功能创建全部层或大量空接口。跨业务模块只能使用公开契约；数据写入由拥有该数据的模块控制。

## 每个业务模块必须明确

1. 输入、输出、拥有的数据、调用者和外部依赖。
2. 业务不变量：授权边界、唯一性、历史可重现、金额 / 计数约束。
3. 状态与合法转换；失败、超时、重试、取消的结果。
4. 事务原子性；跨服务采用的补偿 / 最终一致策略。
5. 接口兼容、错误语义、幂等范围和版本策略。
6. 可验证的性能目标：环境、负载、数据量、分位数与测试命令；未知时先测量，不凭空填“高并发”。
7. 监控、日志敏感级别、恢复负责人和数据恢复方式。

## 变更评审触发条件

新增跨模块调用、公共接口、数据库 ownership、缓存 / 队列 / 服务、新核心依赖、租户策略、长期一致性策略时补 ADR。模块内部按既有边界实现不需要为每个方法写 ADR。

## 自动执行路线

真实 Java 项目将模块映射到包 / 构建模块后，接入 ArchUnit 检查层次、禁止依赖和循环；服务独立发布时引入契约验证。当前治理检查器只验证文档与配置结构，不检查 Java 字节码或业务架构。
