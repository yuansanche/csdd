# 验收与测试规范

## 测试的预期从哪里来

预期来自已确认的需求和业务不变量。Agent 可以协助写测试，但不能按当前实现修改预期后宣布通过。关键验收使用业务负责人确认的案例。对于文档 / 格式修改，链接或格式检查就是对应验证，不机械要求行为测试。

## 按风险选择验证

| 层次 | 验证什么 |
|---|---|
| 单元 | 业务决策、边界、金额 / 时间 / 空值语义 |
| 契约 | 请求 / 响应、错误、兼容、消费者依赖 |
| 集成 | 数据库事务、唯一性、授权、真实外部适配器 |
| 用户流程 | 真实关键路径及失败 / 空 / 加载状态 |
| 架构 | 模块依赖、禁止跨层访问和循环 |
| 发布 | 迁移、冒烟、监控和恢复 |

不是每个功能都跑全部层次；受影响的关键行为必须覆盖。适用的负例包括非法输入、重复请求、权限越界、并发、外部失败与部分成功。

## 测试质量

新增行为优先写会因缺少该行为而失败的案例。断言可观察结果，不只断言内部函数被调用。mock 仅替代难以在该层运行的外部依赖；关键事务 / 集成语义在适合的环境另行验证。

失败先定位根因；不得直接删测试。修缺陷增加能够重现原症状的回归案例。记录选择器、输入、预期和运行报告；检查器只确认映射结构，不理解每个断言。

## 自动化输出

真实业务命令必须在 CI 输出测试收集数量、失败 / 跳过项和报告。配置跳过全部测试但返回 0 的命令不满足规范。必须核对已运行案例和需求映射，必要时检查 JUnit / Playwright 等报告。

本包测试只验证治理检查器的行为，不能代替规则版本发布示例的业务测试。
