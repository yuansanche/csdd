# 开发流程

## 三类变更

| 类别 | 例子 | 最小流程 |
|---|---|---|
| 轻量 | 文档、纯排版、无行为的小修 | 明确范围 → 对应检查 → 差异评审 |
| 常规 | 模块内新增或修改业务行为 | spec 与验收 → plan / tasks → 实现与验证 → PR |
| 高风险 | 权限、资金、公共接口、迁移、跨模块或架构变化 | 常规流程 + ADR / 独立关键预期评审 + 代表性集成 / 恢复验证 |

不机械按代码行数分级。敏感文件改动至少需要相应责任人评审，是否上升业务风险按实际影响判断。

## 从需求到实现

1. 业务负责人确认目标、非目标、验收样例和异常。用 Given / When / Then 或等价的可观察结果描述。
2. `specify` 生成规格；关键歧义通过 `clarify` 收敛。已有规格只更新变化，不重复制造新事实源。
3. 复用检查（C-11）：新增实现前检索项目内现有实现和成熟开源方案，在 spec 的“复用评估”记录结论（直接复用 / 配置 / 适配 / 无满足条件）。
4. 权威实现定位（C-12，仅修改已有功能时）：找出实际接入业务入口的实现，在 spec 的“权威实现定位”记录依据和证据等级（静态确认 / 运行时确认 / 推断 / 未知）。证据不足写“未知”，该需求不得凭猜测进入完成状态。
5. `plan` 说明模块、兼容、依赖、数据与恢复影响；不替需求擅自添加功能。
6. `tasks` 分为可独立验证的小业务切片，标明需求、路径、依赖、修改目标的定位依据和验证命令。禁止用“完善功能”“全面优化”作为无法验收的任务。
7. `analyze` 检查规格、计划与任务冲突。需求质量 checklist 由负责评审的人确认，不由实现 Agent 擅自勾选。
8. `implement` 每次限定一组任务；完成当前切片检查后继续。并行仅用于无依赖且不争用同一文件的任务。
9. `converge` 核对遗漏；修复后执行真实测试。设置本轮时间 / 迭代预算，反复失败时收集根因交给负责人，不无限重写。
10. PR 附验收证据，由 CI 在干净环境执行，再按风险评审。

## 角色与审批（C-13）

同一个人可以承担多个角色，但 Agent 不能批准自己提出的变更。

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| 开发 Agent | 在任务许可路径内实现、修复 | 自批高风险架构或数据结构变更；改动已批准的验收预期 |
| 质量 Agent / 独立验证 | 按验收预期设计并执行测试，出具失败证据 | 为使测试通过而修改业务代码 |
| 协调者 | 调度任务、汇总状态 | 绕过质量门禁把任务标为完成 |
| 架构 / 数据架构 / 发布负责人 | 审查并批准；高风险变更须人工批准 | — |

当前这些约束主要靠人工评审。仓库权限、分支保护和 CI 要由管理员配置（见 [quality-gates.md](quality-gates.md)），本文存在不等于已强制执行。

## 防止长任务漂移

当前需求、任务、已完成项、未解决问题写入仓库文件。会话压缩 / 新会话从这些文件恢复，不能只靠聊天历史。任务范围、验收预期或公共接口发生变化时先更新对应事实源。完成后把缺陷根因转成能够验证的规则或回归案例，不无限增加宏观口号。

## 第一周接入

选择过去出过问题的一个真实功能，建立需求—任务—测试映射。故意制造需求遗漏、失败检查、跨模块依赖和非法输入；确认对应的已接入检测能拦截。暂未接入的架构工具不能算通过该验证。先试点，再推广模板与 CI。
