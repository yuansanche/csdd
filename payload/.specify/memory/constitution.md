# 复杂系统 AI 开发项目宪章

**Version**: 1.2.0 | **Ratified**: 2026-10-13 | **Last Amended**: 2026-10-19

## 适用范围

本宪章约束本项目的人类开发者和编码 Agent。用于新功能、行为变更、缺陷修复和架构演进；纯文档和排版修复按轻流程执行。它规定稳定原则,具体规则放在对应规范与架构文件。上线可用性必须由真实业务检查证明。

## C-01 需求可验证

每个行为变更必须有稳定的需求编号、可观察的验收结果和异常 / 边界样例。业务负责人确认关键预期。影响安全、资金、数据完整性或外部接口的歧义必须先解决；一般实现细节按现有约定选择并记录，不反复等待许可。

执行：spec 模板强制包含验收条件；delivery 检查需求编号与任务、测试映射。映射存在不等于业务正确，预期仍需业务评审。

## C-02 小范围连续交付

每个任务说明修改范围、依赖、需求和验证方式。优先交付一个从输入到可观察结果的业务切片。不得顺便进行无关重构或引入未需要的依赖。越过原任务边界时先记录影响，再更新计划；风险升级时由相应负责人判断。

执行：tasks 模板和 PR 清单；范围变化按风险评审。

## C-03 架构边界可检查

模块职责、依赖方向、数据所有权、事务边界、外部副作用在架构文档中明确。禁止循环依赖、越过模块接口修改其他模块数据和把外部调用混入纯领域规则。改变边界必须有 ADR。

执行：Java 项目接入 ArchUnit 等架构测试；尚未接入时必须标记人工检查，不能宣称自动覆盖。

## C-04 外部规范有明确裁决

本项目的编码规则以 [编码规范](../../docs/standards/coding-standards.md) 为执行依据。Java 工程实践参考阿里巴巴手册，Java 排版采用 Google Java Style 默认模式。重叠规则按 [冲突表](../../docs/standards/external-standards.md) 选择唯一结果；不允许两个格式器互相改写。

执行：自动工具只加载已选择的规则。升级外部指南或工具先评估差异，再经 ADR 修改本项目版本。

## C-05 验证来自业务预期

重要新增行为先固定预期和失败样例，再实现。测试应覆盖适用的正常、非法输入、权限、边界、并发与外部失败情况。涉及真实数据库和服务集成时，关键链路必须在真实依赖或等价测试环境运行。

执行：业务测试、契约测试和必要的集成测试。文档、纯格式变更可以无行为测试，记录原因并运行对应检查。

## C-06 不削弱质量条件获得通过

不得静默删除失败测试、跳过必跑检查、改低门槛、把测试替换成只验证 mock，或按实现现状修改需求预期。合理变更需要独立说明并评审。测试命令退出 0 也要检查是否实际收集并运行了预期测试。

执行：敏感文件负责人评审、CI 重跑、测试报告核验；检查器本身不能判定所有测试内容是否合理。

## C-07 接口、数据和权限保持完整

接口及 schema 变更必须定义兼容策略；重复请求、并发、迁移和故障处理按业务不变量设计。租户 / 用户边界、授权、日志敏感信息和外部输入验证不可缺省。

**数据库结构变更治理**：新增表、字段删除、字段类型修改、约束变更和破坏性数据迁移必须经过数据架构审查。审查必须明确：是否存在重复实体、数据权威来源、兼容性方案、回滚策略和审批依据。未完成审批的高风险 Schema 变更不得通过质量门禁。

**接口契约纪律**：改接口先改已批准的契约（spec 与相关契约文件），再改代码；指令与契约冲突时以契约为准。加字段、加接口属加法变更；删字段、改类型、改必填属破坏性变更，必须由责任人批准并采用扩展—收缩（先并存、迁移下游、再移除）。契约未达到已评审状态，下游不得据此开发。

执行：适用的契约、集成、负例测试；数据迁移在代表性数据上演练。Schema 变更按 [数据治理策略](../../docs/standards/coding-standards.md#数据权限与日志) 和对应 ADR 审查。

## C-08 完成必须有可复现证据

任务勾选表示实现进度，不表示业务验收批准。交付必须关联需求、测试选择器、实际运行结果、代码版本与未验证项。Agent 的完成声明、规格一致性分析和覆盖率数字都不能独立作为商业验收结论。

执行：delivery 按配置执行检查并生成报告；PR 附测试 / 构建证据，人员核对关键结果。

## C-09 发布可观测且有恢复方案

发布前确认版本、迁移、监控、冒烟、回退 / 前向修复与恢复负责人。涉及数据破坏时，仅回退应用镜像不足以恢复业务，必须单独处理数据恢复。

执行：发布检查表和预发演练。生产发布按团队既有授权执行。

## C-10 例外有范围和期限

例外记录包括编号、被豁免规则、原因、风险、补偿措施、负责人、截止日期和复查条件。Agent 不得自动批准自身例外；例外不得通过修改检查器偷偷实现。影响多项目的规范更新先在试点验证。

执行：采用 [例外模板](../../docs/templates/exception.md)，修改敏感配置必须独立评审。初始检查器不自动消费豁免，例外接入需评审后实现。

## C-11 复用优先与已有实现检查

开发新功能前必须检查项目中是否存在满足要求的已有实现、可复用模块或等价能力。不得在未经评估的情况下为相同业务能力创建重复实现。该原则适用于框架自身开发、业务软件开发、开源扩展选型和工具引入。

**已有代码发现**：实现或修改业务能力前，必须检索相关代码、识别主要可复用实现、记录功能边界及证据来源。复用评估结果应包含：可直接复用、需配置调整、需开发适配器、无满足条件的实现。无法证明现有实现位置时，涉及"修复已有功能"的任务不得仅凭猜测进入完成状态。

执行：在 spec 的复用评估和 plan 中记录复用决策，由评审人核对。目前检查器不读取该记录，属人工检查，不能宣称自动覆盖（见 C-03）。复杂项目可采用代码发现工具辅助，但工具推断不能替代业务验证。

## C-12 权威实现识别

修改已有软件时，必须优先定位现有业务实现的实际调用路径和注册入口。不得仅凭文件名、类名或语义相似性推断某个实现正在被业务使用。当系统中存在多个功能相似的实现时，修改前必须根据静态代码分析、配置注册信息或必要的运行时证据，判断哪个实现接入了真实业务入口。

**证据分级**：静态确认（源码、配置）、运行时确认（测试调用、日志追踪）、推断（语义匹配、时间戳）、未知（无法确认）。当证据不足时必须输出"未知"或"证据不足"，不得猜测。修改未接入实际业务的实现后，即使其独立单元测试通过，也不得将对应需求判定为验收通过。

执行：变更计划明确修改目标及定位依据；关键业务修复必须有实际调用路径验证或端到端测试覆盖。

## C-13 角色权限隔离

本项目使用多个逻辑角色完成软件交付。角色可由独立 Agent、工作流或人工负责人承担。主要角色包括：Developer Agent（开发）、Quality Agent（独立验证）、Data Architect（数据审查）、System Architect（架构审查）、Release Owner（发布审批）。

**权限约束**：Developer Agent 不得自行批准自己提出的高风险架构变更或数据结构变更。Quality Agent 不得直接修改生产业务代码以使测试通过。Coordinator 不得绕过质量门禁将任务标记为完成。角色权限应通过工具、工作区、分支保护及 CI 强制执行，而不只是通过提示词定义。

执行：角色与审批表见 [workflow.md](../../docs/workflow.md)，Agent 的停止条件见 [AGENTS.md](../../AGENTS.md)。目前主要靠人工评审；仓库权限、分支保护和 CI 须由管理员配置后才算强制执行。

## C-14 并行工作隔离

多人或多个 Agent 并行时，每个执行者使用独立工作区（如独立 git worktree 或分支），提交的文件必须在任务的“允许修改路径”内，不得顺手修改其他任务许可清单中的文件。并行只用于无依赖且不争用同一文件的任务。

执行：tasks 模板的允许修改路径字段；评审时核对 diff 与许可路径。目前无自动检查，属人工检查。

## C-15 重复问题必须落为规则

同一类问题第二次出现时，不得只在沟通中提醒，必须落为可检查的载体之一：AGENTS.md 禁止条款、自动检查或 lint 规则、回归测试、模板或 SKILL，并记录落点。无法自动化的，明确标注由人工检查。

执行：缺陷复盘记录问题类别与落点；未落地不得以“已知问题”关闭。

## 治理

宪章原则变更由业务 / 架构 / 交付责任角色共同确认；同一人可以承担多个角色。普通业务细节在功能 spec 中调整。发现宪章、规格、契约或代码冲突时报告具体位置，回到负责该内容的文档修正，不能依靠隐含解释绕过。

变更记录必须写版本、日期、影响的模板和检查。规范优先级与 ADR 不能覆盖本宪章的稳定原则；确需改变原则时正式修改本文件。
